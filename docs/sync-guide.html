Engineering & product reference

How Conifer Syncs Your Notes

A walkthrough of what actually happens, in what order, and which server files are touched, whenever Conifer synchronizes across devices — written for engineers who'll work on it and for anyone who needs to understand what it does without reading Kotlin.

In short

The five-sentence version, for anyone who won't read the rest of this page.

●
Your own storage, no vendor lock-in Notes sync to any Nextcloud account the user already has, as plain files. There is no Conifer server in the loop.
●
Offline-first The app is fully usable with no network. Sync is an optional background job that reconciles the device with the server.
●
No conflict pop-ups If the same note is edited on two devices while offline, sync resolves it automatically — no dialog, no manual merging.
●
Cheap when nothing changed An idle sync round costs exactly one network request, regardless of how many notes exist in total.
●
Human-readable backups, for free Alongside the machine data, Conifer writes plain Markdown files a person can open directly in Nextcloud's file browser.
●
Deletions are reversible for 90 days Deleting a note doesn't erase its file immediately — it's a safety window in case another device hasn't seen the deletion yet.

Key terms, at a glance

The handful of words that come up constantly below. A complete alphabetical glossary is at the end.

WebDAV

A standard way for apps to read, write, and list files on a remote server over HTTP — the same protocol Nextcloud's own desktop and mobile clients use. Conifer speaks it directly; no Conifer-specific server component is required.

ETag

A short fingerprint the server hands back for a file or folder, which changes whenever its contents change. Comparing ETags lets Conifer tell "nothing changed" from "something changed" without downloading anything.

Bucket

A monthly folder (e.g. 2026-07) that notes created in that month are filed into. Buckets let sync check "did anything in July change?" as a single question instead of one per note.

Tombstone

What a deleted note becomes: its file stays on the server, marked "deleted": true, instead of being removed immediately. This gives every device time to notice the deletion before the file is ever actually erased.

Last-write-wins

The rule that decides which version of a note survives when it was edited on two devices independently: whichever edit has the later timestamp wins, with a fixed tiebreaker if they're identical.

Readable file

A plain .md Markdown file, one per day, generated purely for humans to browse. It's a by-product of sync, never an input to it — editing it directly has no effect and will be silently overwritten.

Where your notes live

Everything sits under one configurable root folder in the user's Nextcloud storage — Conifer by default, changeable per device in Sync Settings.

Conifer/ ← "appRoot", user-configurable ├── 2026-06/ ← readable, for humans │ ├── 2026-06-01.md │ └── 2026-06-17.md ├── 2026-07/ │ └── 2026-07-26.md └── .sync/ ← machine data, hidden by the dot-prefix ├── bits/ ← the actual source of truth │ ├── 2026-06/ │ │ ├── 3f7a1c2e-....json │ │ └── 91bd44aa-....json │ └── 2026-07/ │ └── 550e8400-....json └── meta/ └── manifest.json ← written once, marks the folder as Conifer's

The split is deliberate. Opening the Conifer folder in the Nextcloud web UI or a file manager shows only the month folders full of readable Markdown — that's the layout meant to be browsed by a person. Everything sync actually reads and writes for its own bookkeeping lives under .sync/, which most file browsers and the Nextcloud desktop client hide or skip by default because of the leading dot.

Not a security boundary

The dot-prefix only hides .sync/ from casual browsing. A user with "show hidden files" turned on can see it, and Conifer always addresses it explicitly. It exists to keep the human-facing folder clean, not to restrict access.

A note's monthly bucket is fixed forever at creation time and never changes, even if the user later edits the note or moves its display date — so a note is never physically moved between folders, only its content is updated in place.

One sync round, end to end

Every time sync runs, it works through the same six stages in order. Only one sync round can run at a time per device.

flowchart LR
    A["① Fast-path check"] -->|"nothing changed"| Z(["Done — 1 request"])
    A -->|"something changed"| B["② Pull"]
    B --> C["③ Push"]
    C --> D["④ Render readable files"]
    D --> E{"⑤ GC due?\n(weekly)"}
    E -->|"yes"| F["Remove old tombstones"]
    E -->|"no"| G["⑥ Finalize"]
    F --> G
The full round used by every sync trigger below — a busy round runs all six stages; a quiet one exits after stage ①.
  1. Fast-path check

    Ask the server for the current ETag of the .sync/bits folder. If it's identical to the one recorded after the last sync, and there's nothing locally waiting to be pushed, stop here — the whole round cost one request.

  2. Pull

    List the monthly bucket folders and their ETags. For every bucket whose ETag has changed since last time, list its files and download only the ones whose individual ETag is new, merging each into the local database.

  3. Push

    Upload every note created or edited locally since the last sync. Brand-new notes go up as a batch; edits to existing notes are written conditionally so a concurrent edit elsewhere is never silently overwritten.

  4. Render readable files

    Regenerate the Markdown file for every day touched by this round's pulls and pushes, and upload the ones that actually changed.

  5. Garbage-collect tombstones

    Once a week, permanently remove notes that were deleted more than 90 days ago and whose deletion has already reached the server.

  6. Finalize

    Re-read the bits folder's ETag (this round's own pushes changed it) and store it, along with the current time, so the next round's fast-path check has something to compare against.

What starts a sync round

Trigger Behavior
Manual The "Sync now" button in Sync Settings.
Just connected Immediately after a device links to a Nextcloud account for the first time.
After an edit 10 seconds after the local notes change, so a burst of edits triggers one round, not many.
Periodic Every 5 minutes while the app is open, standing in for an "app came to the foreground" signal.

Sync itself is entirely opt-in — until a device is connected to a Nextcloud account, none of this runs and the app behaves exactly as it does without the feature.

How ETags are actually used

ETags are the mechanism that lets Conifer avoid re-downloading data that hasn't changed, at three different levels of granularity.

sequenceDiagram
    participant App as Device
    participant NC as Nextcloud (WebDAV)
    App->>NC: PROPFIND .sync/bits (Depth 0)
    NC-->>App: ETag "a1b2c3"
    alt ETag same as last sync AND nothing waiting to push
        App->>App: Stop — nothing to do
    else ETag differs, or local edits are pending
        App->>App: Continue to Pull (step 2)
    end
Level 1 — the root fast-path check, one request per sync round when nothing has changed anywhere.

The same idea repeats at two finer levels once the fast path doesn't apply:

  • Per bucket: each monthly folder has its own ETag. Comparing it against the one recorded at the last sync tells Conifer whether it needs to look inside that month at all — a year of untouched history costs nothing beyond listing its folder names.
  • Per file: each note's own ETag is compared against the value stored alongside it locally. Only files whose ETag actually differs get downloaded.
Why not just compare timestamps?

An ETag captures the server's own notion of "this content changed," independent of clock skew between devices or of exactly what changed. It also doubles as a safe write guard (see Pushing changes): the server can be told "only save this if the ETag is still X," which is how Conifer avoids ever silently overwriting someone else's edit.

One rule keeps this whole scheme honest: ETag comparison only ever applies to .sync/bits. The human-readable Markdown files are never consulted for change detection — writing them (step 4) must never make the fast-path check in the next round think something changed when it didn't.

Pulling changes from the server

Step 2 of the sync round — bringing remote changes onto the device.

sequenceDiagram
    participant App as Device
    participant NC as Server
    App->>NC: List .sync/bits/ (folders + ETags)
    NC-->>App: 2026-06 (etag X), 2026-07 (etag Y changed!)
    loop only buckets whose ETag changed
        App->>NC: List .sync/bits/2026-07/ (files + ETags)
        NC-->>App: 3 files, 1 with an unseen ETag
        App->>NC: Download that one file
        NC-->>App: note content
        App->>App: Merge into local database
        App->>App: Remember 2026-07's new ETag
    end
Up to 6 files download at once when several have changed, to keep a bulk pull fast without overwhelming the server.

Every downloaded note runs through the same merge rule before it's stored, whether or not the local device had its own unsynced edit to that note. Once a bucket's files have all been checked, its folder ETag is recorded — that's what lets the next sync round skip the whole month with a single comparison.

Pushing local changes

Step 3 — sending what changed on this device, without ever clobbering someone else's edit.

Brand-new notes (never before synced) are uploaded together in one batch request where possible, since their file names are unique by construction and can't collide with anything already on the server. Edits to existing notes are written one at a time, each conditioned on the file's last known ETag: 

sequenceDiagram
    participant App as Device
    participant NC as Server
    App->>NC: Save file, but only if its ETag is still "a1b2c3"
    alt Still matches — no one else touched it
        NC-->>App: Saved. New ETag: "d4e5f6"
        App->>App: Mark this note clean
    else Someone else saved it first
        NC-->>App: Rejected (412 Precondition Failed)
        App->>NC: Download the current version
        NC-->>App: current content + its ETag
        App->>App: Resolve via last-write-wins
        Note over App: If the local edit still wins,
retry the save (up to 3 times)
    end
The "only if the ETag still matches" condition is what makes concurrent edits from two devices safe by construction.
Write condition Meaning Used for
If-None-Match: * Save only if the file doesn't exist yet Uploading a brand-new note
If-Match: <etag> Save only if the file's ETag is still this exact value Uploading an edit to an existing note

A note that keeps losing this race (three failed attempts) is left marked for the next sync round rather than forced through — nothing is ever lost, it just waits.

Resolving conflicts: last-write-wins

What decides the winner when the same note was genuinely edited on two devices before they could sync.

flowchart TD
    Q1{"Does this device know\nthis note at all?"}
    Q1 -->|"No"| R1["Take the server's version"]
    Q1 -->|"Yes"| Q2{"Does this device have\nan unsynced edit to it?"}
    Q2 -->|"No"| R2["Take the server's version\n— it's simply newer"]
    Q2 -->|"Yes — real conflict"| Q3{"Compare edit times"}
    Q3 -->|"Server's edit is later"| R3["Server's version wins"]
    Q3 -->|"This device's edit is later"| R4["This device's version wins"]
    Q3 -->|"Identical to the second"| Q4["Tiebreaker: compare device IDs"]
    Q4 --> R5["Higher device ID wins\n(same result on every device)"]
Applied per note, never field-by-field — the whole note is either kept or replaced, and unknown fields from a newer app version are always preserved either way.

Deleting a note is just another kind of edit for this purpose: a later deletion beats an earlier text edit, and a later text edit un-deletes a note that was deleted earlier — there is no special case for tombstones in the merge rule itself.

Why this needs no user prompt

The rule is fully deterministic: given the same two versions of a note, every device computes the same winner independently, with no coordination and no "which one do you want to keep?" dialog. The trade-off, accepted deliberately for now, is that the loser's specific wording is discarded rather than offered for manual reconciliation.

The readable Markdown files

Step 4 of the sync round — a pure by-product with no influence on sync itself.

For every day that had a note pulled, pushed, or deleted this round, Conifer regenerates that day's Markdown file from scratch and compares its hash against what was uploaded last time. Identical content is skipped without a request; only days that actually changed get re-uploaded.

<!-- Automatically generated by Conifer. Manual changes will be overwritten. --> # 2026-07-26 ## 09:14 — Morning thought Coffee first, emails second. --- ## 13:40 — Meeting notes Discussed the Q3 roadmap with the team.
2026-07/2026-07-26.md — always sorted the same way, always rendered the same way, on every device.

Because rendering is fully deterministic — same notes always produce byte-identical Markdown — two devices regenerating the same day never disagree about what it should contain. That's what makes it safe to write this file unconditionally, with no ETag check and no conflict handling: whichever device's write lands last, the bytes are the same either way.

Not an editing channel

These files are generated, never read back and never merged. Editing one directly in Nextcloud has no effect on the actual notes — it will simply be overwritten the next time that day is re-rendered.

Deleting notes & garbage collection

Why a deleted note doesn't disappear from the server right away.

flowchart LR
    A["Note deleted\non Device A"] --> B["File stays put,\nmarked deleted"]
    B -->|"synced"| C["Every connected device\nnow sees it as gone"]
    C -->|"90 days pass"| D["Weekly cleanup job\nremoves the file for good"]
The 90-day window is the safety margin: it's how long a device could plausibly stay offline and still get an honest chance to see the deletion before the file is gone for good.

This two-phase approach — mark, then later remove — exists because a device that's offline when a note is deleted has no way to be told "this file used to exist." If the file were removed immediately, that device would eventually reconnect, still see the note locally, and re-upload it as if it were new: an unintended "resurrection" of something the user deliberately deleted.

The cleanup pass itself runs at most once a week, and only physically removes a deletion that has already reached the server — never one that's only recorded locally.

Known limitation

A device that stays offline for longer than the 90-day window can still, in principle, run into a stale local edit whose file was already cleaned up elsewhere. Today's mitigation is conservative: such an edit is simply left pending rather than risking a resurrection. A proper resolution surface (flagging it for the user to confirm) is planned but not yet built.

Connecting a device

How a device first links to a Nextcloud account — no password is ever typed into Conifer itself.

sequenceDiagram
    actor U as User
    participant App as Conifer
    participant NC as Nextcloud
    App->>NC: Start a login session
    NC-->>App: One-time login link
    App->>U: Open that link in the system browser
    U->>NC: Log in and approve Conifer
    App->>NC: "Is the login finished yet?"
    NC-->>App: Yes — here's a device-specific app password
    App->>App: Store it in the OS-secured credential store
    App->>App: Run the first sync round
Nextcloud's own "Login Flow v2" — the same mechanism its official desktop and mobile clients use.

The credential Conifer ends up storing is a Nextcloud app password: a credential scoped to this one login, which the user can revoke from their Nextcloud account at any time without changing their real password. It's kept in the platform's own secure storage — Android Keystore, Apple Keychain, or the desktop OS's credential manager — never in the same database as note content.

When that secure storage isn't available

On some desktop environments (for instance, a Linux machine with no reachable OS keyring), Conifer falls back to a weaker, software-only store and warns the user before connecting, so the trade-off is a deliberate, visible choice rather than a silent downgrade.

Edge cases worth knowing about

Situations that come up in practice and how sync is designed to behave in each.

Situation Behavior
First device ever, empty Nextcloud folder Creates the folder structure and a one-time manifest.json marker; tolerates another device winning the race to create it first.
New device joining an existing account Downloads every existing note across all monthly buckets (in parallel, up to 6 at a time) before it has anything of its own to push.
Clocks slightly out of sync between devices Only shifts the winner of rare, close-timed conflicts; the deterministic tiebreaker keeps the outcome consistent across devices either way.
Someone edits a note's file directly in Nextcloud Treated exactly like an edit from another device. If the edited file can't be parsed, it's skipped and logged — never overwritten blindly.
Someone edits a readable Markdown file directly Silently overwritten the next time that day is re-rendered — the file's own header says as much.
A note's format is newer than this app version understands Left completely untouched, locally and remotely, rather than risk corrupting data this version can't fully interpret.
Server unreachable The sync round aborts cleanly and the app keeps working entirely on local data; nothing is left half-written.
Sync interrupted mid-round (app killed, network drop) Every stage is safe to redo — the next round simply starts over and converges, with no duplicates and no lost edits.

Full glossary

Every sync-specific term used on this page, alphabetically.

App password
A Nextcloud credential scoped to one connected app or device, generated during login, that the user can revoke independently of their main account password.
Bucket
A monthly folder (yyyy-MM) that a note is filed into based on its creation date, fixed forever at creation and never changed afterward. Lets sync check a whole month for changes in one request.
Conditional write (If-Match / If-None-Match)
An instruction attached to a save request telling the server to only go through with it if a stated condition still holds — e.g. "only if the file's ETag is still X," or "only if this file doesn't exist yet." The mechanism that makes concurrent writes from two devices safe.
Dirty
The internal flag on a note meaning "changed on this device but not yet successfully uploaded." Cleared only once the server has confirmed the write.
ETag (entity tag)
A short, opaque fingerprint the server assigns to a file or folder, which changes whenever its content changes. Comparing ETags is far cheaper than comparing file contents directly, since it needs no download.
Fast-path check
The very first thing a sync round does: compare the current root ETag against the one recorded last time. If it matches and nothing local is waiting to be pushed, the round ends immediately.
Garbage collection (GC)
The periodic pass (at most weekly) that permanently deletes tombstoned notes once they've been retained long enough that every device has had a fair chance to see the deletion.
Last-write-wins (LWW)
The conflict-resolution rule: when the same note was edited independently on two devices, the edit with the later timestamp wins, with a fixed tiebreaker (comparing device IDs) if the timestamps are identical.
Login Flow v2
Nextcloud's standard browser-based login handshake for third-party apps: the app opens a one-time link in the system browser, the user signs in there, and the app receives an app password once approved — the user's real password is never typed into the app.
Manifest
A small manifest.json file, written once when a Nextcloud folder is first used for sync, recording the data format version in use.
Merge
The act of reconciling a note just downloaded from the server with whatever this device already has for it, applying the last-write-wins rule when both sides changed.
PROPFIND
The WebDAV request used to ask the server for information about a file or folder — its ETag, whether it's a folder, and its immediate contents — without downloading the file itself.
Readable module
The part of sync that generates the human-facing Markdown files, one per day, as a derived by-product. Never read back, never merged, purely generated.
Root folder (appRoot)
The single top-level folder in the user's Nextcloud storage that all of Conifer's data — readable and machine — lives under. Conifer by default; configurable per device.
Tombstone
A deleted note's file, kept on the server with a deleted: true marker instead of being removed right away, so every device gets a chance to see the deletion before garbage collection erases it for good.
WebDAV
The standard HTTP-based protocol Conifer uses to read, write, and list files on a Nextcloud (or any WebDAV-compatible) server — the same protocol Nextcloud's own official clients use.

Reflects the sync engine as implemented. The full engineering specification this implementation follows lives at docs/nexcloud_sync_spec.md in the repository, for anyone who needs the exact algorithms and data formats.
